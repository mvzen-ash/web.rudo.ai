Why we built Rudo.ai self-hosted first

A multi-tenant SaaS product is the faster thing to ship. One deployment, one database, one bill for us to manage instead of asking every user to run their own. We considered it, and we didn't build it that way — on purpose.

The data problem that SaaS doesn't solve

A security-scanning platform sees things most software never touches: open ports, exposed endpoints, internal service names, sometimes fragments of the application logic itself. Sending all of that through a third party's infrastructure — even a well-run one — adds a dependency most teams evaluating a pentesting tool would rather not take on.

Self-hosting via Docker Compose means the scan data, the findings, and the generated reports stay on a server you already control. The only thing that optionally leaves your network is whatever you explicitly send to a cloud AI provider — and even then, Data Masking strips IPs and email addresses first.

What we gave up to get there

Self-hosting isn't free. You're responsible for the server, for Docker, for updates, for backups. That's a real tradeoff, and it's not the right one for every team — if you want zero infrastructure to manage, Rudo.ai isn't currently built for you.

But for the teams we built this for — small, technical, already comfortable running Docker Compose for other things — owning the deployment was worth more than the convenience of a hosted dashboard.

What this means going forward

Local deployment stays the default. If a hosted option ever makes sense for teams that explicitly want it, it'll be an addition, not a replacement — the self-hosted path isn't going away.
